# DLink 下载器 · GUI 信息架构与界面构成设计

> 状态：设计稿 v1（2026-11-15）
> 性质：**只描述界面与信息结构，不含代码，不选技术栈。**
> 定位：**个人自用**的网盘直链下载器（扩展取直链 → 本机下载器下载），不是企业级下载管理器。
> 读者：实现 GUI 的人（用来决定「界面上要摆什么、每个数怎么算、什么状态下显示什么」）。
>
> 本文所有数字均取自 `docs/PLATFORMS.md`、`docs/BAIDU-SPEEDTEST.md`、`docs/FINDINGS.md` 与本仓库现有实现（`src/dlink/server.py`、`src/dlink/models.py`、`src/dlink/downloader.py`、`extension/`）。凡是我推出的、不是实测的，都标了「推算」，别当实测用。

## 0. 设计基准（先定三条，后面所有取舍都从这里推）

### 0.1 这个工具的「真相来源」只有三样东西

| 序号 | 真相 | 用户最常问的问题 | 界面必须回答的方式 |
|---|---|---|---|
| 1 | **这个任务在动吗、多快、什么时候完** | 「卡住了吗？」 | 进度 + 速度 + 剩余时间，且**速度必须可信**（见 §1.1） |
| 2 | **链接还有效吗、过期了能救回来吗** | 「要不要我干什么？」 | 「直链有效期」一列 + 过期后的**自动续链**状态（见 §3.3） |
| 3 | **为什么这么慢，是我的问题还是网盘的问题** | 「是不是这软件有毛病？」 | 平台徽标 + 限速类型说明 + 速度对比（见 §4） |

个人自用工具的三个前提，直接决定了设计取向：
- **用户就是作者**。不需要「向导式引导」「小白文案」「一屏只讲一件事」。**信息密度优先**。
- **但不能只有日志**。日志能排错但不能一眼看到「哪个任务在拖后腿」，所以需要**表格 + 可排序列**。
- **不需要账号、同步、云配置、多用户、权限**。设置项都写本机，改完即时生效即可。

### 0.2 窗口模型：主窗口唯一，其余全是模态/抽屉

```
┌ 主窗口（常驻，可最小化到托盘）──────────────────────────────┐
│  顶栏：全局状态条                                           │
│  ① 工具条：新建 / 暂停全部 / 续传全部 / 打开目录 / 设置        │
│  ② 任务列表（可分组折叠）  ← 主视区，占 70% 以上面积          │
│  ③ 底部状态栏：汇总数字 + 引擎版本 + 端口                     │
└─────────────────────────────────────────────────────────────┘
      ↓ 选中一行
   [右停靠抽屉：单任务详情]  ← 默认收起；宽屏(≥1200px)可改为常驻
      ↓ 点设置
   [设置窗口：模态，左分类右表单]
```

**为什么主窗口只有一个**：这是自用工具，用户 90% 的时间只看「在下载什么、还要多久」。多窗口、多标签页、多面板（像 qBittorrent 那样侧栏切「全部/下载中/已完成」）在这里是净负担——任务数通常 < 20 个。

**为什么详情用抽屉而不是新窗口**：详情里有个「复制直链」「立即续链」这种要边看列表边点的操作；独立窗口会挡住列表。

### 0.3 中文术语表（全文统一，实现时别再换词）

| 术语 | 用词 | 不用 |
|---|---|---|
| 一个待下载的文件 | **任务** | 条目、作业、job |
| 一次「扩展推送过来的一批文件」 | **批次** | 包、组、batch 展示成「文件夹」 |
| 直链 | **直链**（必要时「下载直链」） | 地址、URL |
| 链接还在有效期内 | **直链剩余 X 小时** | 有效期、TTL |
| 链接过期后自动向扩展换新的 | **自动续链** | 刷新、重取、relink |
| 分段并行的并行数 | **线程数**（沿用用户口语），括号注「分段并发」 | 并发度、workers（设置里可注英文，正文不注） |
| 校验通过 | **校验通过（SHA1）** | 验证成功 |

> 用「线程数」而不是「并发数」：用户实际调这个数是照着 `BAIDU-SPEEDTEST.md` 里「1/3/8 路分别 75/130/9 KB/s」的口语来的，跟他看到的名词保持一致比正确更重要。设置项旁边一行小字写清「= 同时下载的分段数」。

# 第一部分 · 完整信息清单

清单按「谁的属性」分成四级：**任务级 / 批次级 / 全局级 / 设置级**。每条都写：**用户为什么需要它 / 什么时候需要 / 精确到什么粒度**。最后给一个「必须 vs 可有可无」的总表（§1.5）。

## 1.1 任务级信息（列表一行 + 详情）

### 1.1.1 文件名 `name`

- **为什么需要**：唯一能让人认出「这是哪个文件」的字段。
- **什么时候需要**：始终。
- **粒度**：全名可见（两行折行或末尾省略 + 悬停显示完整路径）。**不要**只显示前缀——网盘分享里 `xxx.part1.rar` / `xxx.part2.rar` 很常见，省略掉序号等于没显示。
- **特殊情况**：拿不到文件名时显示 `(未命名) B7K2`（后 4 位取任务 ID 尾部），**不能显示空**——空行会让用户以为是 bug。
- **落盘重名**：实现里已有「重名自动加 `(1)`」逻辑，界面**必须把最终落盘名显示出来**（详情里给「保存为」一行），否则用户会在下载完成后找不到文件（`PC.7z` 变成了 `PC(1).7z`）。

### 1.1.2 大小 `size`

- **为什么需要**：判断「这值不值得等」。1.5GB 在 80KB/s 下是 5.4 小时，用户看到大小就能自己算账。
- **什么时候需要**：任务进列表时就显示（推送时扩展已带 `size`）。
- **粒度**：`1.48 GB` / `28.3 MB` / `812 B`。**3 位有效数字**，单位 KB/MB/GB 二进制（1024）。不要显示成 `1583673344 字节`。
- **大小未知时**：显示 `大小未知`（灰色），进度条改为**不定态**（左右流动的条纹），不要显示 0%。当前实现里有 `_probe_size()` 探测逻辑，探测成功后再变成确定进度。

### 1.1.3 进度 `progress`

- **为什么需要**：一眼看出「还要多久」和「是不是卡住了」。
- **粒度**：
  - **数字**：整数百分比，`37%`。不上小数——个人工具里 37.2% 和 37% 对决策没区别。
  - **图形**：细进度条，高度 6–8px。**分段任务要能看出分段**：进度条上叠一层等分的竖线（1.5GB / 32MB ≈ 47 段），否则用户看到「47 个分段并行，进度条却一格一格跳」会觉得没在动。
  - **字节数**：`547 MB / 1.48 GB`，放在详情里，列表里不占位。
  - **已完成的任务**：进度条换成一个对勾，**但保留 100% 位置**，避免行高跳动。
- **未开始（排在队列里）**：进度条显示为空的灰槽，不是 0% 的实心条。

### 1.1.4 速度 `speed` ★ 本文最关键的一条

- **为什么需要**：用户判断「慢是网盘限速还是软件坏了」「暂停/继续有没有用」「改线程数有没有变快」的唯一依据。速度显示的**抖动**会直接摧毁信任。
- **什么时候需要**：`下载中` 状态时每 1 秒刷新；`暂停/等待/失败` 时显示 `—`（不要显示 0 KB/s，0 会让人以为卡死了）。
- **精度与算法（必须按这个来）**：

  | 项 | 规定 | 理由 |
  |---|---|---|
  | 刷新频率 | **每秒刷新 1 次** | 更高频率人眼也读不了，还费 CPU |
  | 采样间隔 | **1 秒采一个字节增量** | 底层是 `progress` 回调累计的 `done` 字节，天然有值 |
  | 平滑方式 | **最近 3 个采样点的滑动平均，但不是算术平均** —— 用「最近 3 秒总增量 ÷ 3 秒」 | 直接算瞬时值在百度 80KB/s 时会出现 `0 / 240 / 0 / 160` 的抖动（分段边界、TCP 拥塞窗口都在作妖） |
  | **但要在停顿时立刻归零** | 若 **最近 3 秒内增量 < 1 KB**，速度直接显示 `0.0 KB/s`，并**在 5 秒后把状态改成 `疑似卡住`**（见 1.1.6） | 平滑的代价是掩盖真实停顿——5.4 小时的下载里，掩盖停顿比数字抖动更危险 |
  | 小数位 | 按量级定：`< 1 MB/s` 保留 **1 位**（`80.2 KB/s`）；`≥ 1 MB/s` 保留 **1 位**（`9.7 MB/s`）；`≥ 100 MB/s` 取整 | 百度 80.2 和 80.9 的差别对用户有意义（判断有没有被降速）；9.7 和 9.8 没有 |
  | 单位 | **恒用 KB/s 或 MB/s，不用 Kibit/s，不用 KBps** | — |
  | 多分段任务 | 显示**所有分段之和**，不是平均值 | — |
  | 暂停后恢复的前 3 秒 | 显示 `…`（采样不足） | 避免恢复瞬间显示一个虚高的值，然后掉下来 |

  > 一个具体的坑：百度官方限速是「精确 80.0 KB/s，40 秒零波动」。如果你用 1 秒瞬时值，用户会看到 `0 / 240 / 0 / 240` 的锯齿，然后以为工具在骗他。用 3 秒窗口后稳定显示 `79.8–80.3 KB/s`，用户自己就能得出「这是服务端硬限」的结论——**这正是画像里「教育性设计」最省力的实现方式：让数字自己说真话。**

### 1.1.5 剩余时间 `ETA`

- **为什么需要**：这是用户离开电脑/去睡觉的决策依据。1.5GB @ 80KB/s = 5.4 小时，用户需要知道「今晚能不能下完」。
- **精度与算法（必须按这个来）**：

  | 项 | 规定 | 理由 |
  |---|---|---|
  | 公式 | `剩余字节 ÷ 平滑后速度` | 用**与显示同一个**平滑速度，否则 ETA 会和速度自相矛盾 |
  | 显示格式 | `4 小时 12 分` / `12 分 30 秒` / `< 1 分钟` | **超过 1 小时不进位到秒**。`4:12:37` 给人虚假的精确感，实际波动 ±20 分钟 |
  | 何时显示 | **下载满 10 秒后才显示**；之前显示 `估算中…` | 前 10 秒速度在爬升，ETA 会从「3 天」跳到「5 小时」，比不显示还糟 |
  | 何时隐藏 | 速度 = 0 且状态 `疑似卡住` → 显示 `—（无进度）` | 除零会得到「∞」，界面上出现 ∞ 是灾难 |
  | 防抖 | 只有当新 ETA 与已显示值相差 **> 30 秒**（或跨越小时边界）时才刷新文本；否则保持显示旧值 | ETA 每秒钟从 5 小时 12 分跳到 4 小时 58 分是**最招人烦的**一类界面抖动 |
  | 悲观估计 | 详情里额外给一个「按当前速度推算的最晚完成时间」= **现在时间 + ETA**（绝对时刻，如 `明天 03:40`）。进度面板上的 ETA 是相对的，详情里给绝对值 | 用户的真实问题是「我明早起来能下完吗」，需要的是挂钟时间 |
  | **直链过不去的场次** | 若 `ETA > 直链剩余有效期`，ETA 数字变**橙色**，并在旁边挂一个小三角提示（见 §4.4） | 这是本工具最重要的「提前警告」，详见 §4.4 |

### 1.1.6 状态 `status`

这是信息架构里最容易做错的地方：**「失败」必须拆类**，因为不同失败对应完全不同的用户动作。

| 状态 | 中文显示 | 用户动作 | 列表配色 | 备注 |
|---|---|---|---|---|
| `queued` | 等待中 | 无 | 灰 | 排在别的任务后面 / 用户暂停了队列 |
| `starting` | 连接中 | 无 | 蓝（转圈） | 已发起请求，还没拿到第一个字节。**≤ 3 秒正常，超过 10 秒要提示**（可能 cookie 快照错了） |
| `running` | 下载中 | 可暂停 | 蓝 | — |
| `stalled` | **疑似卡住** | 见 §3.2 | 黄 | 自动判定的派生状态，不是独立后端状态：速度 0 持续 **≥ 30 秒**。旁边必须挂具体原因（`已 45 秒无字节`） |
| `need_refresh` | **等待续链** | 等扩展自动来取（或手动点） | 橙 | 后端已有这个状态位；扩展每 **30 秒**轮询 `/api/pending-refresh` |
| `paused` | 已暂停 | 继续 | 灰 | 用户主动暂停 |
| `verifying` | 校验中 | 无 | 蓝 | **这一状态必须独立**：1.5GB 算 SHA1 要十几秒到一分钟，期间进度条是 100% 但速度是 0。不给独立状态的话用户一定以为卡死了。显示「校验中（SHA1）…」+ 一个独立的不定态小条 |
| `done` | 已完成 | 打开文件夹 | 绿 | 附「校验通过（SHA1）」或「仅大小校验」 |
| `failed` | 失败 | 重试 / 看详情 | 红 | 附**错误码 + 一句话**（见 1.1.9） |
| `expired` | **链接已失效** | 重新取链 | 红（带橙描边） | 这是失败的一种，但**单独成类**：用户动作是「回浏览器重新点一下」，不是「重试」 |

- **粒度**：状态用 2 个字，加上下文；**不要**把「已下载 0 字节 / 正在建立连接」当状态文案，那是详情里的日志。
- **多状态并存**：一个任务同一时刻只有一个主状态；`stalled`、`need_refresh` 是**叠加在 `running` 之上的告警**——实现上建议列表「状态」列显示主状态，告警用小图标叠加在同一格，避免列宽爆炸。

### 1.1.7 来源平台 `platform`

- **为什么需要**：决定「慢不慢正常」「线程数能不能调」「续链靠不靠得住」。这是**限速差异的唯一线索**，必须常驻可见。
- **什么时候需要**：始终可见（列表一列）。
- **粒度**：**文字 + 色标**，如 `百度` / `夸克` / `微云` / `UC`。用 3–4 个字的色块标签，**不用图标**——个人工具里为一个平台画 icon 的成本远大于收益，而且图标识别度不如「百度」两个字。
- **配色建议**：微云=青、百度=蓝、夸克=紫、UC=橙。**色弱用户**必须能靠文字区分，色块仅作次级线索。

### 1.1.8 保存路径 `path`

- **为什么需要**：用户要「打开所在文件夹」；也要知道是 C 盘还是 D 盘。
- **什么时候需要**：列表里**不显示**（占宽，且几乎不变）；详情里显示完整路径，顶部工具条显示「本次任务的根目录」。
- **粒度**：详情里给**完整绝对路径**（可复制）。列表的工具条右侧显示当前默认目录的缩写（`D:\Downloads\DLink`）+ 「更改」按钮。

### 1.1.9 错误信息 `error`

- **为什么需要**：这是「不能简陋到无法排错」的兑点。
- **粒度（必须给三层）**：

  | 层 | 位置 | 内容 | 举例 |
  |---|---|---|---|
  | 一句话摘要 | 列表「状态」列后 | ≤ 16 字，人话 | `链接已失效` |
  | 错误码 + 原始信息 | 详情「错误」区 | `[E_LINK_EXPIRED] 下载直链返回 HTTP 403（段 3），链接已失效或鉴权缺失` | 直接展示，不美化 |
  | 建议动作 | 详情「错误」区下一行 | `→ 点「重新取链」；若反复出现，检查是否在浏览器里登录过该账号` | 对应 `DLinkError.hint` |

- **必须区分的错误类型**（对应代码里已有的异常）：

  | 异常 | 码 | 列表摘要 | 建议动作 |
  |---|---|---|---|
  | `LinkExpired` | `E_LINK_EXPIRED` | 链接已失效 | 自动续链 / 手动重新取链 |
  | `IntegrityError` | `E_INTEGRITY` | 校验失败 | **文件保留**，可 `verify` 复核；不要自动重下（会再耗 5 小时） |
  | `NotLoggedIn` | `E_NOT_LOGGED_IN` | 未登录 | 去浏览器登录，再点扩展按钮 |
  | `AuthRequired` | `E_AUTH_REQUIRED` | 需要提取码 | 回分享页输入提取码后再提取 |
  | `DLinkError` 其它 | 原码 | 下载失败 | 见 hint |
  | 网络类 | 无 | 网络超时 | 已自动重试 N 次（`retries` 默认 6）；可手动重试 |

### 1.1.10 直链有效期 / 续链信息 ★ 本工具特有，必须有一列

- **为什么需要**：这是整个项目最核心的约束。用户必须能一眼看出「哪几个任务快过期了」，因为它决定了「今晚哪些能下完、哪些会断」。
- **什么时候需要**：**常驻一列**（见 §2.2 列设计）。这是与普通下载器最大的差别，不能藏进详情。
- **粒度**：
  - 显示 `剩余 6.2 小时`（1 位小数）或 `剩余 12 分`（< 1 小时时精确到分）。
  - > 2 小时：正常色；**≤ 2 小时**：橙；**≤ 15 分钟**：红；已过期：`已过期`。
  - 拿不到 `expires_at` 时（**当前实现里百度/夸克都返回 `expires_at=None`**，见 §6 矛盾 1）显示 `未知`（灰），并且**不要把这一列隐藏**——`未知` 本身是有价值的信息：它意味着「这个任务没法提前警告，只能靠 403 事后兜底」。
  - 续链进行中：显示 `续链中…（已等 12 秒）`，换行显示`上次成功：21:03`。
- **为什么精确到 0.1 小时**：8 小时 vs 6 小时是 2 小时差；但用户的下载可能就在 20 分钟这个尺度上卡边。0.1 小时 ≈ 6 分钟，够用。

### 1.1.11 线程数 / 分段信息 `workers` / `segments`

- **为什么需要**：这是用户唯一能调的「提速旋钮」，也是解释「为什么百度只给 1 路」的载体。
- **什么时候需要**：列表里**不占列**（个人工具，20 行 * 一列全是 1 或 8 是噪音）；详情里显示，且**可改**（改后需重启该任务的分段，要提示）。
- **粒度**：
  - 详情里：`线程数 8（平台建议 8）`，用户改成别的值后显示 `线程数 3（平台建议 8，自定义）` 并给一行警告。
  - **越界警告必须硬性写死**：百度改成 > 1 时立即红字 `百度为账号级限速，超过 1 路会触发 403 风控，实测 8 路降到 9 KB/s`。这不是「建议」，是实测结论，要在界面上重复一次。

### 1.1.12 校验信息 `verified_by`

- **为什么需要**：网盘下载最常见的信任问题是「文件坏了没」。
- **粒度**：完成时显示 `校验通过（SHA1）` / `校验通过（MD5）` / `仅大小校验` / `无校验信息`。四种结果**颜色不同**：前两个绿，第三个灰，第四个黄（黄 = 文件可能是坏的，用户应该自己验一下）。
- **详情里**：实际 SHA1、期望 SHA1 都显示，并给「复制 SHA1」按钮。文件魔数（`7z`）也显示——实现里 `sniff_magic()` 已经在做，是免费的排错信息。

### 1.1.13 时间戳（创建 / 完成）

- **为什么需要**：排错时「这个任务挂了多久了」；以及「昨天那个 3GB 的还在不在」。
- **什么时候需要**：列表里默认**不显示**（可开列）；详情里显示 `创建 21:03:44 / 完成 02:41:12 / 耗时 5 小时 37 分`。
- **粒度**：列表里若开启，用 `昨天 21:03` 这种相对+绝对混合；详情里用完整 `2026-11-15 21:03:44`。

### 1.1.14 批次归属

- **为什么需要**：一次推送 100 个文件时，用户要能「整个批次暂停/删除」，而不是点 100 次。
- **粒度**：批次名 = 分享标题（如 `PC 游戏整合`）或 `百度分享 1Dxxx`。列表里以**分组头**出现（见 §3.4）。

## 1.2 批次级信息（一次扩展推送 = 一个批次）

| 信息 | 为什么需要 | 粒度 |
|---|---|---|
| 批次名 | 识别「这批是哪来的」 | 分享标题，取不到就用 `平台 + 分享ID前 6 位` |
| 文件数 | 「100 个文件里几个成功了」 | `已就绪 82 / 取链失败 18 / 共 100` |
| 批次总大小 | 判断要不要一次全下 | `合计 42.49 GB`（取不到大小的文件不计入，注明 `（另有 3 个大小未知）`） |
| **取链失败文件清单** | 扩展端 `maxLinks` 截断或单文件取链失败时，这些文件在下载器里**根本不存在** | 批次头上一行 `18 个未取到直链` + 点开列出文件名和原因 |
| 批次状态 | 折叠时也要知道里面在不在动 | 折叠时聚合显示 `3 个下载中 · 2 个已完成` 和一条聚合进度条 |

> **关键**：批次里「取链失败的文件」这是最容易丢信息的地方。当前 `injected.js` 会给失败文件塞 `error: '未取直链（数量超出单次上限）'`，但 `server.py` 的 `/api/task` **会直接跳过没有 `url` 的 item**，失败信息就永远到不了 GUI。**设计方案强制要求：推送失败清单在扩展侧（popup）显示，且批量推送时把失败清单随任务一起或单独投递到下载器 GUI 的「上一批未取到直链」提示条。**（见 §6 矛盾 3）

## 1.3 全局级信息（顶部状态条 + 底部状态栏）

| 信息 | 位置 | 为什么需要 | 粒度 | 刷新 |
|---|---|---|---|---|
| 总速度 | 顶部状态条，最左最大 | 一屏之内知道「现在有多快」 | 同 §1.1.4 的 3 秒平滑；多任务求和 | 1 秒 |
| 活跃任务数 | 顶部状态条 | 「队列还有几个在跑」 | `3 下载中 / 2 等待 / 1 失败` | 状态变化时 |
| **下载器连接状态** | 顶部状态条，最右 | 决定「扩展推任务会不会失败」。扩展靠 `GET /api/health` 探测 | `● 已就绪 · 8765` / `● 未连接` / `● 端口冲突` | 5 秒心跳 |
| 端口 | 连接状态旁边 | 排错时（防火墙、端口占用）必须知道 | `8765`（从 `8765–8769` 里实际占用的那个） | 变化时 |
| 剩余磁盘空间 | 底部状态栏 | 5.4 小时下到一半磁盘满了，是真实会发生的 | `D: 剩余 128 GB`（**1 位小数不重要，取整到 GB**）；**< 任务总大小 1.5 倍时变红** | 30 秒 |
| 今日/本次流量 | 底部状态栏（可选） | 「今天下了多少」——个人工具有用但非必需 | `本次 12.3 GB` | 10 秒 |
| 引擎版本 | 底部状态栏 | 报错时的第一句话 | `DLink 0.1.0 · Python` | 启动时 |
| 系统通知开关 | 顶部状态条 | 完成后想被叫醒 | 图标 toggle | — |

**为什么「剩余空间」必须靠前（底部状态栏但常驻可见）**：`BAIDU-SPEEDTEST` 的情景就是 1.5GB 下 5.4 小时。一个下到 98% 才遇到「磁盘满」的用户，损失的是 5 小时。这条是小成本大收益的必做项。

**为什么连接状态用「●已就绪」而不是弹窗**：扩展侧在下载器没启动时会直接报「下载器没有运行，请先启动」。GUI 侧要做的不是重复报警，而是**让用户随时能确认它还活着**。所以是常驻的一个小圆点 + 端口，点一下可以做一次健康检查并显示耗时。

## 1.4 设置级信息（每一项都要有「为什么」）

设置窗口按「最常改的在上」排，三组：**下载 / 平台策略 / 高级**。

### 组 A · 下载（用户最常改）

| 设置项 | 为什么需要 | 默认值 | 粒度 / 控件 | 必须? |
|---|---|---|---|---|
| 默认保存目录 | 90% 的下载都去同一个地方 | `%USERPROFILE%\Downloads\DLink` | 路径 + 「浏览」按钮 + 显示该盘剩余空间 | **必须** |
| 完成后动作 | 「早上起来文件已经在那」 vs 「下完自动关机」 | `无`（下拉：无 / 打开文件夹 / 打开文件 / 关机 / 播放提示音） | 下拉单选；**关机必须二次确认**（第一次勾选时弹一次「确实要在全部任务完成后关机？」） | **必须**（关机可延后到 v0.2） |
| 同时下载的任务数 | 微云 8 路单任务就 9.7MB/s；多任务并行会互相抢带宽 | `2` | 1–5 数字框 | 应该 |
| 校验方式 | 校验要花时间（1.5GB SHA1 约 10–60 秒） | `优先 SHA1 → MD5 → 仅大小` | 下拉三选 | 应该 |
| 完成后保留分段文件 | 断点续传依赖 `.parts` 目录 | `否`（完成后清理） | 开关 | 可有可无 |

### 组 B · 平台策略（这个工具的核心差异化）

| 设置项 | 为什么需要 | 默认值 | 粒度 | 必须? |
|---|---|---|---|---|
| 每平台线程数 | 唯一提速旋钮 | 微云 8 / 百度 1 / 夸克 6 / UC 6 | 每个平台一行：`平台 · 线程数 [数字框] · 平台建议 8`，**超建议值立即红字警告** | **必须** |
| 每平台限速（KB/s） | 用户想给某个平台留带宽 / 避免触发风控 | 全部 `不限` | 数字框 + `不限` 开关 | 应该 |
| 夸克「窗口期/限流期」判定阈值 | 夸克是二阶段限速，实现里暗示要能降级 | `聚合速度连续 60 秒不增长则降级到 1 路` | 开关 + 秒数 | v0.3 |
| **是否在直链剩余 < N 小时时提前续链** | 提前换链能避免「跑到一半 403」 | `开，阈值 1 小时` | 开关 + 小时数 | 应该（见 §4.4） |

### 组 C · 高级（排错用，默认折叠）

| 设置项 | 为什么需要 | 默认值 | 粒度 | 必须? |
|---|---|---|---|---|
| 代理 | 本机出口 IP 被网关拦过（`FINDINGS` 记录微云 403 待换网络复测） | 跟随系统 | `不使用 / 系统代理 / 手动 host:port` + 「测试」按钮 | 应该 |
| 监听端口范围 | 8765–8769 可能全被占 | `8765–8769` | 文本 `8765-8769` | 可有可无 |
| 重试次数 | 网络抖动 | `6` | 数字框 | 可有可无 |
| 分段大小 | 微云依赖「32MB × 8 路」这个经验值 | `32 MB` | 下拉 8/16/32/64 | 可有可无（但**必须可读**，因为它是微云 9.7MB/s 的关键，用户排错时会想看） |
| 日志级别 / 打开日志文件 | 排错 | `信息` | 下拉 + 按钮 | 应该（个人工具靠日志排错） |
| 随机 UA / 伪装客户端 | 夸克、UC 必须伪装 PC 客户端 | `跟随平台` | 下拉 | 可有可无（默认正确即可） |

### 明确**不要**的设置项

多语言、主题皮肤、快捷键自定义、开机自启的复杂策略、云同步配置、账号登录、任务优先级排序规则、代理自动切换、限速计划表。**理由是：自用工具里这些配置的维护成本大于使用收益**，加进去会让「设置窗口」从 3 组变成 8 组，用户（就是作者）反而找不到「默认保存目录」。

# 第二部分 · 界面结构

## 2.1 主窗口布局（分区与优先级）

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ ① 状态条 (高 40px)                                                            │
│   9.7 MB/s ▲   3 下载中 · 2 等待 · 1 失败          ● 已就绪 · 8765    [通知]   │
├──────────────────────────────────────────────────────────────────────────────┤
│ ② 工具条 (高 36px)                                                            │
│  [＋ 新建任务] [⏸ 全部暂停] [▶ 全部继续] │ 保存到 D:\Downloads\DLink [更改] │ 🔍筛选│
├──────────────────────────────────────────────────────────────────────────────┤
│ ③ 任务列表（主体，纵向滚动）                                                   │
│ ┌ 百度 · PC 游戏整合 · 42.49 GB · 82/100 就绪 · 3 下载中 ─────── [▾][⏸][✕] ┐ │
│ │ 名称                大小     进度              速度        剩余     直链   │
│ │ DATA01.7z           1.48 GB  ██████░░░ 37%  80.1 KB/s   3 小时 26 分 6.2h │
│ │ DATA02.7z           2.10 GB  ██░░░░░░░ 12%  79.8 KB/s   5 小时 12 分 6.2h │
│ └──────────────────────────────────────────────────────────────────────────┘ │
│ ┌ 微云 · 素材包 · 1.53 GB · 8/8 就绪 · 2 下载中 ───────────────────── [▾] ┐  │
│ │ ...                                                                      │  │
├──────────────────────────────────────────────────────────────────────────────┤
│ ④ 状态栏 (高 24px)  D: 剩余 128 GB · 本次流量 12.3 GB · DLink 0.1.0 · 端口 8765│
└──────────────────────────────────────────────────────────────────────────────┘
```

**为什么这么排（优先级从上到下递减）**：

1. **总速度在最左上角**——人眼先看左边。这是「现在怎么样」的最大一个字。
2. **工具条第二行，且按钮少**——「新建任务」是罕见操作（任务 99% 由扩展推送），所以放在左边但不是最大按钮；**「全部暂停」必须显眼**：用户经常需要临时掐掉全部下载去开视频会议，一个「暂停全部」比逐个点 8 次有用得多。
3. **列表占 70%+ 面积**——这是唯一的主视区。**不为它做左右分栏导航**（像 qBittorrent 的侧边「全部/下载中/已完成」）。理由：任务数通常 < 20，一屏就能看完，用筛选代替导航。筛选做成工具条上的一个下拉（`全部 / 进行中 / 失败 / 已完成`），而不是常驻侧栏。
4. **连接状态放右上**——它是「环境健康度」，不是高频信息，但因为「扩展推不进来」是最常见的困惑，必须常驻可见。点它展开一个 8 行的小浮层：健康检查耗时、端口、扩展最后心跳时间、日志路径。
5. **底部状态栏给「环境信息」**——剩余空间、版本、端口。这些是排错时才看，但必须一眼能找到。

**窗口尺寸**：默认 1100×620，最小 900×480。**最小宽度 900 是有意义的**——任务表 8 列在这个宽度下刚好不挤（见 2.2）。低于这个宽度，GUI 应当**隐藏「来源平台」和「直链剩余」两列**（见 2.2 拥挤策略），而不是让所有列都变窄。

**高 DPI**：自用工具常在高分屏，进度条 6px 在 150% 缩放下会变成 9px，注意别糊。

## 2.2 任务列表设计

### 2.2.1 默认列（8 列，从左到右）

| # | 列 | 宽 | 内容 | 可排序 | 说明 |
|---|---|---|---|---|---|
| 1 | ☐ | 24px | 复选框 | — | 批量操作。**表头有全选**，作用于**当前可见（按批次/筛选后）**的行 |
| 2 | 名称 | ★ 弹性（最小 180px） | 文件名 | ✅ 字母序 | 唯一吃满剩余宽度的列。悬停显示完整路径的 tooltip |
| 3 | 平台 | 56px | 色块+字（`百度`） | ✅ | 点击表头可只显示该平台 |
| 4 | 大小 | 80px | `1.48 GB` | ✅ 数值序 | 右对齐（数字必须右对齐，否则小数点对不齐，扫视困难） |
| 5 | 进度 | 140px | 条 + `37%` | ✅ | 数字右对齐 |
| 6 | 速度 | 90px | `80.1 KB/s` | ✅（按当前速度） | 右对齐。**速度排序有隐含陷阱**：已完成的显示 `—`，排序时空值永远排最后 |
| 7 | 剩余 | 100px | `3 小时 26 分` | ✅ | 右对齐。快到时橙色 |
| 8 | 直链 | 90px | `6.2 h` | ✅ | **最右侧**。因为它是「长期不变的属性」，变化频率最低，放最边不干扰主要扫视路径 |

**列序的设计理由**：从左到右按「标识 → 属性 → 动态 → 警示」排。用户扫视顺序是「这是什么 → 多大 → 到哪了 → 多快 → 还要多久 → 会不会断」，最后两列（剩余、直链）是**决策区**，紧邻，便于横向对比。

**为什么「直链」不放在第 3 列（更醒目）**：它变动极少（每小时看一次就够）。放在第 3 列会打断「名称 → 大小 → 进度」这条最热的扫视路径。用**颜色**（临近过期变橙/红）代替**位置**来做注意力抢占，是更便宜的做法。

### 2.2.2 可选列（默认关闭，设置里能开）

保存路径、开始时间、耗时、SHA1 前 8 位、线程数、错误码、批次名。**理由**：自用工具里有人想随时看 SHA1，但不该默认占宽。列表头右键菜单给「显示列…」。

### 2.2.3 排序

- 默认排序：**按状态分组**（下载中 → 等待 → 需要续链 → 失败 → 暂停 → 已完成），组内按**创建时间倒序**。这不是纯字段排序，而是「派生分组 + 组内排序」。理由：用户最关心「正在动的」，而不是「字母序第一的」。
- 点任意列头：切换为**纯字段排序**（升/降）。
- **「已完成」组默认折叠**，只在组头显示 `已完成 12 个 · 合计 18.4 GB`。理由：已完成的任务是历史噪音，但用户偶尔要回去「打开文件夹」，所以折叠而非删除。
- 异常高亮不参与排序：`链接已失效`/`失败` 永远置顶（在「进行中」之上）——**这是「异常优先」的唯一例外，值得违反排序规则**。

### 2.2.4 拥挤时的处理（三条明确的降级阶梯）

自用工具也会遇到 100 行 × 小窗口。规则要写死，不能靠自适应：

| 触发条件 | 行为 |
|---|---|
| 窗口宽 < 1000px | 隐藏「直链」列，改为在「剩余」列后加一个 ⏰ 小图标（只有临期/过期才出现） |
| 窗口宽 < 900px | 再隐藏「平台」列，平台色块并入名称左侧的小圆点 |
| 单行行高不足 / 名称过长 | 名称**双行折行**，行高从 32px 变 40px；**不省略**（见 1.1.1） |
| 行数 > 50 | 启用虚拟滚动（只渲染可见行）。**必须**，否则刷新进度会卡 |
| 列总宽 > 可用宽 | 名称列压到 180px 后**出现横向滚动条**，不压缩其它列 |

### 2.2.5 行的视觉状态

| 状态 | 行样式 |
|---|---|
| 下载中 | 白底；进度条蓝色；左侧 3px 蓝色竖条 |
| 已暂停 | 灰底（#F5F5F5），文字降一档；左侧灰色竖条 |
| 失败/已失效 | 白底；左侧 3px 红竖条；文件名旁红色 ⚠ |
| 已完成 | 白底；名字灰色（弱化）；左侧绿色竖条（或对勾） |
| 选中 | 整行淡蓝高亮 + 左侧竖条加深；**不改变任何列的位置**（避免跳动） |
| 疑似卡住 | 黄色左侧竖条 + 速度列 `0.0 KB/s` 加黄底 |

**关键：任何状态的视觉变化都不能改变行高或列宽。** 刷新 1 次/秒的列表里，只要有一行行高变化，整个列表就会上下抖，盯 5 小时会疯。

## 2.3 单任务详情（右抽屉，宽 380px）

选中一行后从右侧滑出。分 4 块，**信息密度高，无引导文案**：

```
│ 实际    a1b2c3d4e5f6…                   [复制]   │
│ 期望    a1b2c3d4e5f6…                            │
│ 魔数    7z ✅                                    │
├ 直链 ─────────────────────────────────────────┤
│ 剩余    6 小时 12 分    [立即续链]               │
│ 状态    ✅ 有效                                  │
│ 域名    d.pcs.baidu.com                          │
│ Cookie  BDUSS ✓ STOKEN ✓ BDCLND ✓                │
├ 时间线 ───────────────────────────────────────┤
│ 21:03:44  收到任务（扩展推送）                    │
│ 21:03:45  开始下载 线程 1                        │
│ 22:31:10  段 12 重试 1/6（超时）                 │
│ 02:41:12  下载完成，开始校验                      │
│ 02:41:58  校验通过（SHA1）                       │
└────────────────────────────────────────────────┘
```

**每一块的存在理由**：

- **「文件」块的 SHA1/魔数**：这是本工具的核心卖点（三位一体校验），必须展示。复制按钮是给「拿去跟别人对一下」的场景。
- **「直链」块的 Cookie 清单**：这是**排错能力的核心**。网盘下载 90% 的失败是「少了一个 cookie」（`STOKEN` 缺失 → `errno:-6`；缺 `FTN5K` → 401）。只显示「✓/✗」不显示值，既安全又足够定位问题。**这正是「不能简陋到无法排错」的具体落点。**
- **「时间线」而不是「日志」**：完整日志在文件里，详情里给**事件摘要**（开始/重试/暂停/续链/校验）。理由：5.4 小时的下载会产生几千行日志，全贴进 UI 没人看；但用户需要知道「22:31 重试过一次」。
- **没有的东西**：下载速度曲线图、分段瀑布图（哪个段先完成）——v0.1 不做。图上信息量不抵实现成本，且个人工具里「总速度 + 段数」已足够定位。

## 2.4 设置窗口

- **模态**，尺寸 640×520，左「分类」右「表单」。三组对应 §1.4（下载 / 平台策略 / 高级）。
- **改完即时生效**（个人工具不需要「确定/取消」的仪式感），但**每项下方一行小字注明生效范围**：
  - `默认保存目录` → `对新建任务生效，已在下载的任务不受影响`
  - `每平台线程数` → `对之后开始的任务生效；正在下载的任务需在该任务详情里单独改`
  - 这种「生效范围说明」比「确定按钮」有用一百倍——用户改了个设置不生效是最常见的困惑。
- **平台线程数那一组的排布**：四个平台横向排列成表格，每行 `平台 | 线程数[8] | 平台建议 8 | 一句话说明`。说明文案直接抄实测：
  - 微云：`连接级限速，单连接 ~14MB 后掉到 240 B/s。8 路并行实测 9.7 MB/s。`
  - 百度：`账号级限速 80 KB/s。超过 1 路会触发 403，实测 8 路降到 9 KB/s。`
  - 夸克：`二阶段限速。18–23 点限流期约 1.8 MB/s，建议 6 路。`
  - UC：`同夸克，未实测。`

  这不是装饰文案，是**整个工具的价值主张在界面上的唯一落点**。用户看一眼就知道每个平台该怎么调。

## 2.5 空状态

### 2.5.1 首次启动（还没收到过任何任务）

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│                          ↓                                       │
│                    还没有下载任务                                 │
│                                                                  │
│   1. 在浏览器里打开百度 / 夸克 / 微云的分享页                     │
│   2. 点页面右下角的「↓ 提取直链」                                 │
│   3. 点浏览器工具栏的扩展图标 → 「发送到下载器」                   │
│                                                                  │
│   下载器状态：✅ 已就绪（127.0.0.1:8765）  [自检]                 │
│   扩展状态：  ✅ 已连接（2 分钟前）                               │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```
- **必须有三步说明**（这是唯一需要引导的地方：用户刚装完不知道要去浏览器点）。
- **必须有「扩展状态」**：这是自检的关键——如果扩展从没连过（`/api/health` 从没被带 `chrome-extension://` origin 的请求打过），就显示 `从未连接 · 检查扩展是否启用`。空状态是**唯一有空地**放这个诊断信息的地方。

### 2.5.2 空筛选结果

不显示大插画，只在列表区中央一行灰字：`没有符合条件的任务（当前筛选：失败）  [清除筛选]`。

### 2.5.3 已完成组折叠时的空态

`已完成 0 个`。不要隐藏组头——组头本身是「我知道这里本来该有东西」的信号。

## 2.6 错误与降级状态（三层）

| 层 | 场景 | 表现 |
|---|---|---|
| **全局横幅**（顶部，黄色/红色，可关闭但 30 秒后重现） | 磁盘剩余 < 任务总量 × 1.5；100% 端口冲突；扩展 5 分钟内无心跳 | `⚠ D 盘剩余 2.1 GB，仍有 8.4 GB 待下载  [暂停全部] [换目录]` |
| **行内** | 单任务失败/失效/卡住 | 见 §2.2.5 行样式 + 状态列具体原因 |
| **每任务详情** | 具体错误 | 三层错误信息（§1.1.9） |

**降级原则**：任何时候，**就算所有任务都失败，界面也不能变白/变空**。失败任务永远在列表里（红竖条），用户能做的事（重试、重新取链、打开文件夹）永远在右键菜单里。

## 2.7 托盘与最小化（自用工具的必要项）

- 关闭主窗口 = **最小化到托盘**（首次关闭时提示一次「已最小化到托盘，右键图标退出」，可勾「不再提示」）。
- 托盘图标 tooltip：`DLink · 3 下载中 · 9.7 MB/s`。
- 托盘右键：`显示窗口 / 全部暂停 / 全部继续 / 退出`。
- **托盘图标叠加进度环**（v0.3，可选）：Windows 10+ 支持，对「后台长期下载」体验提升明显。

# 第三部分 · 关键交互流程

## 3.1 扩展推送任务进来时：**直接开始，但要给可见的「刚收到」反馈**

### 决策
**不做确认弹窗。** 理由：推送的动作本身（用户在扩展 popup 里点「发送到下载器」）就是确认；再加一次确认是重复劳动，且 100 个文件时弹 100 次是灾难。

**但是**：必须有「收到」的反馈，且必须告诉用户**这次收到几个、总共多大**——因为这是唯一能发现「扩展只推了 20 个但分享有 100 个」的机会。

### 流程（ASCII）

```
扩展 popup 点「发送到下载器」
        │
        ▼
POST /api/task {items:[...]}
        │
        ▼
┌─ 下载器 GUI ────────────────────────────────────────┐
│ ① 主窗口若在托盘 → 不抢焦点；托盘图标闪一下 + 气泡    │
│    气泡文案：已收到 100 个文件 · 42.49 GB             │
│ ② 列表顶部插入新批次组（高亮 1.2 秒淡出）             │
│ ③ 状态条活跃数 +100，总速度开始跳                     │
│ ④ 若「同时下载任务数」已满 → 新任务显示「等待中」      │
└──────────────────────────────────────────────────────┘
```

### 新批次组的两种形态

**① 小批次（≤ 5 个文件）**：直接展开，不建组头。

```
│ DATA01.7z    1.48 GB  ███░░░░░ 37%  80.1 KB/s  3h26m   6.2h │
│ DATA02.7z    2.10 GB  █░░░░░░░ 12%  79.8 KB/s  5h12m   6.2h │
```

**② 大批次（> 5 个文件）**：建组头，**默认折叠到「摘要 + 前 3 行」**。

```
┌ 百度 · PC 游戏整合 · 42.49 GB · 82/100 就绪 · 3 下载中 ─── [▾ 展开全部] ┐
│ ✅ 已取到直链 82 个（其中 18 个取链失败，点击查看）                     │
│ DATA01.7z    1.48 GB  ██████░░ 37%  80.1 KB/s  3h26m          6.2h     │
│ DATA02.7z    2.10 GB  ██░░░░░░ 12%  79.8 KB/s  5h12m          6.2h     │
│ DATA03.7z    1.92 GB  ░░░░░░░░  0%  等待中     —              6.2h     │
│ … 还有 79 个                                                          │
└────────────────────────────────────────────────────────────────────────┘
```

> **注意「6.2h」在这三个任务上是一样的**——因为它们来自同一次推送、同一批直链，`expires_at` 相同。**这是设计上的一个机会**：同批任务的直链过期时间是共享的，因此可以在**组头**上只显示一次 `直链剩余 6.2h`，行内不重复 100 次。这既省列宽也更好读。**规则：批次内所有任务的有效期相同 → 组头统一显示，行内该列留空。**（见 §6 矛盾 6：语义上「同批一定同有效期」不完全成立，实现需按值判断）

## 3.2 下载中的任务：暂停 / 继续 / 删除

### 入口（三处，都要有）

1. **右键菜单**（主力入口）：`暂停 / 继续 / 重新取链 / 打开所在文件夹 / 复制直链 / 复制 SHA1 / 删除任务 / 删除任务和文件`
2. **详情抽屉底部按钮**：主操作一个（`暂停` 或 `继续`），其余在 ⋯ 菜单。
3. **键盘**：`空格` 暂停/继续选中行，`Delete` 删除（弹确认），`Ctrl+A` 全选。

### 暂停的语义（这里有个坑必须写清）

```
点「暂停」
   │
   ├─ 当前状态 = 下载中 → 立即停止写入，状态 → 已暂停
   │      · 已下载的分段和 .parts 文件保留（断点续传的前提）
   │      · 速度列 → —（不是 0.0，见 §1.1.4）
   │      · 进度百分比**保持不变**，进度条变灰
   │
   ├─ 当前状态 = 校验中 → 不能暂停（已完成下载）。
   │      · 按钮置灰，tooltip：校验中无法暂停
   │
   └─ 当前状态 = 已完成 → 按钮变成「重新下载」
```

**关键约束：暂停不销毁断点。** 1.5GB 的任务暂停后必须能续传，否则用户不敢暂停。界面上要让这个「安全感」可见：暂停的行在详情里显示 `已保留 37 个分段（547 MB），可续传`。

### 继续

```
点「继续」
   │
   ├─ 直链仍有效（剩余 > 5 分钟）→ 直接续传，状态 → 连接中 → 下载中
   │      · 进度条从原位置继续（不是从 0）
   │
   ├─ 直链已过期或剩余 < 5 分钟 → **不要直接开下**
   │      · 状态 → 等待续链，立刻写入 /api/pending-refresh 队列
   │      · 显示：等待扩展续链…（扩展每 30 秒轮询）
   │      · 若 60 秒内扩展没来取（可能浏览器关了）→ 转为橙色提示
   │         「扩展 60 秒未响应 —— 请打开浏览器」  [手动重新取链]
   │
   └─ 直链未知（expires_at = None）→ 直接开下，靠 403 兜底
```

**为什么「剩余 < 5 分钟」就换链而不是硬冲**：百度 80KB/s 下，5 分钟的链接只能下 24MB，接下来必然 403。提前 5 分钟续链，比失败后重试省一次完整失败流程。这 5 分钟阈值是**推算**的工程值，可调。

### 删除

| 动作 | 行为 | 确认 |
|---|---|---|
| 删除任务 | 移出列表，删除 `.parts` 分段，**保留已完成的成品文件** | 不确认（可撤销：底部出现 5 秒 toast `已删除 1 个任务 [撤销]`） |
| 删除任务和文件 | 同时删成品文件（进回收站） | **二次确认**，明确写文件名和大小 |
| 清空已完成 | 批量移除已完成任务（不删文件） | 不确认 |
| 删除正在下载的任务 | 先暂停再删，超 3 秒未停 → 强制断连并标记 | 不确认 |

**为什么「删除任务」不弹确认**：自用工具里删除单个任务的成本极低（重新从浏览器点一次就有），弹窗只会拖慢。用**可撤销的 toast** 代替弹窗，是更合适的成本结构。但「删文件」必须确认，那是不可逆的。

## 3.3 直链过期时：**尽量别让用户看到它**

### 三层防线（按优先级）

```
                     ┌── 第 1 层：提前续链（静默）──┐
任务开始下载时记下 expires_at
   → 若 ETA > 剩余有效期，或剩余 < 阈值（默认 1 小时）
   → 主动发起续链请求，但**不暂停下载**（旧链接还能用，边下边换）
   → 界面上只在详情里出一行：`已提前换取新直链（21:03）`
   → 用户根本不需要知道这件事发生过
                     └──────────────────────────┘
                                  │ 失败
                                  ▼
                     ┌── 第 2 层：403 兜底（半自动）──┐
downloader 抛 LinkExpired（HTTP 401/403）
   → 状态 → 等待续链（橙）
   → 保留所有分段（进度不丢！）
   → 写入 /api/pending-refresh
   → 扩展 30 秒内轮询取走 → 重新解析 → 回填新链接
   → 自动恢复下载，状态回 下载中
   → 详情时间线记两行：
        03:12:45  直链返回 403，已请求续链
        03:13:10  收到新直链，恢复下载（分段 47 个保留）
                     └──────────────────────────┘
                                  │ 扩展不在 / 用户关了浏览器
                                  ▼
                     ┌── 第 3 层：明确的人工提示 ──┐
等待续链 > 60 秒
   → 行变红，状态「链接失效 · 扩展未响应」
   → 顶部横幅：`⚠ 2 个任务的直链已失效，浏览器扩展未响应`
                `[打开浏览器重新提取]  [稍后]`
   → 右键菜单的「重新取链」可用（会重新写入队列并强制扩展再轮询）
   → **不自动删除、不清空进度**
                     └────────────────────────┘
```

### 关键 UI 文案（列表状态列）

| 阶段 | 状态列显示 | 颜色 |
|---|---|---|
| 提前续链中 | `下载中`（不变，只在详情里加一行） | 蓝 |
| 403 已触发 | `等待续链 12s` | 橙 |
| 续链成功 | `下载中` | 蓝 |
| 60 秒无响应 | `链接失效 · 需扩展` | 红 |
| 续链多次失败 | `续链失败 3 次` | 红（详情里给最后一次的错误码） |

### 一个必须避免的反模式

**不要弹模态框说「链接已过期，请点击确定」。** 5.4 小时的下载里可能发生 3–5 次，模态框会打断一切（包括用户的小电影）。**全部用行内状态 + 顶部横幅**。这是「个人自用工具」与「企业产品」在交互上最大的分野之一：后者怕用户不知道，前者怕用户被打断。

## 3.4 多文件任务（100 个文件）：防刷屏的三条硬规则

### 规则 1：按批次分组，组默认折叠到前 3 行

见 §3.1 的 ASCII。**组头永远可见**（含聚合进度），行内只展开前 3 行 + `… 还有 79 个 [展开]`。

### 规则 2：同批次同进度的行**合并显示**（仅折叠态）

100 个文件里 80 个在「等待中」，没必要 80 行。折叠态给**状态聚合**：

```
│  ▸ 82 个文件在队列中（合计 38.1 GB）· 等待中 · 平台建议 1 路     │
│  ▸ 18 个文件未取到直链  [查看清单]                                │
```

**展开后**则一律逐行显示，不做任何合并——用户展开就是要看明细。

### 规则 3：批量操作挂在组头，不挂在工具栏

组头右侧：`[⏸ 全部暂停] [▶ 全部继续] [✕ 删除批次] [⋯ 更多]`。
**理由**：工具栏的「全部暂停」是全局的（所有批次），组头的是本批次的。两个层级不能混。

### 100 个文件时的性能与体验约束

| 约束 | 值 | 为什么 |
|---|---|---|
| 默认同时下载数 | 2 | 100 个任务同时开 = 100 × 8 条连接 = 800 连接，会被平台掐，本机也扛不住 |
| 折叠状态下渲染行数 | ≤ 6 | 保证「3 个批次 × 6 行 + 组头」在一屏内看完 |
| 进度刷新 | 整表 1 Hz 统一刷新，**不是每行独立定时器** | 避免 100 个定时器 |
| 展开 100 行时 | 虚拟滚动 + 刷新降到 2 秒一次（可配置） | 动的作用是「看得见在动」，2 秒足够 |

### 另一个容易被忽略的：**「取链失败」的 18 个文件**

它们没有 `url`，下载器侧**根本收不到**。但用户会在分享页看到 100 个文件，回到下载器只有 82 个，会以为丢数据了。所以：

- 组头第一行必须写：`✅ 已取到直链 82 个 / ⚠️ 未取到 18 个`（`total` 字段扩展侧有）。
- 点 `18 个未取到` → 弹一个清单：文件名 + 原因（`未取直链（数量超出单次上限）` / `该文件需要单独提取` / `API 返回空`）。
- 清单底部给操作：`[重试这 18 个]`（走 §3.3 的续链通道）。

## 3.5 首次使用引导（仅此一处，且不做分步向导）

不做「欢迎页 → 下一步 → 下一步」。自用工具装完就去用了。只做两件事：

1. **空状态里的三步文字**（§2.5.1）+ 扩展连接自检。
2. **首次收到任务时的一次性提示**（toast，非模态）：
   `百度适合 1 路线程（账号级限速 80KB/s），已在设置里按平台配置好。`
   一次即够，之后不再出现。

> **判断依据**：如果用户是作者本人，这些提示甚至多余；但如果是「隔了三周再打开」，三步文字能省掉翻文档的时间。所以只在空状态和首次出现，不重复。

# 第四部分 · 针对限速特性的设计

## 4.1 核心目标：让「慢」有解释，而不是有抱怨

用户看到 80KB/s 时的第一反应必然是「这软件坏了」。设计任务不是隐藏慢，而是**在用户抱怨之前把答案放在他眼前**。

### 4.1.1 三个具体手段（按成本从低到高）

| 手段 | 实现成本 | 效果 | 做不做 |
|---|---|---|---|
| **① 速度数字本身做得稳**（§1.1.4 的 3 秒平滑） | 极低 | 用户看到 `79.8 / 80.1 / 80.2` 恒定，自己就会得出「这是服务端硬限」的结论 | **必须** |
| **② 平台徽标常驻 + 详情里的一句话解释** | 低 | 把「慢」和「平台」关联起来 | **必须** |
| **③ 首次遇到某平台慢速时，详情里出一行注解** | 低 | 补充定量证据 | 应该 |

### 4.1.2 注解的具体文案（写在任务详情的「平台」小卡里）

**百度（速度稳定在 80KB/s 附近时自动出现）：**
```
百度是账号级限速，实测恒定为 80.0 KB/s（40 秒零波动）。
换直链、换 CDN、改 UA、加线程全部无效；8 路并发反而触发 403 降到 9 KB/s。
这不是软件问题。
```

**微云（速度 > 5 MB/s 时不显示；速度掉到 < 1 MB/s 且持续时间 > 30 秒时显示）：**
```
微云是连接级限速：单条连接约 14 MB 后掉到 240 B/s。
当前可能是分段未充满或连接数不足。建议线程数 8（32 MB × 8 段，实测 9.7 MB/s）。
```

**夸克（速度明显下降时）：**
```
夸克是二阶段限速：
  窗口期 15–20 MB/s（多连接有效）
  限流期 约 1.8 MB/s（18:00–23:00 多见，总量恒定）
现在处于限流期，增加线程数不会更快。
```

> **文案写作原则**：给**数字**（80.0 KB/s、14 MB、1.8 MB/s）而不是形容词（「比较慢」）；给**否定结论**（「换 CDN 无效」）而不是「请耐心等待」；结尾一句「这不是软件问题」——这是用户心里真正想问的那句话，直接回答。

## 4.2 平台限速差异在 UI 里的体现（4 个位置）

| 位置 | 体现方式 | 为什么在这里 |
|---|---|---|
| **① 列表「平台」列** | 色块 + 文字，常驻 | 让用户把「慢」「平台」两个信息并在视野里 |
| **② 任务详情的「平台」卡片** | 限速类型 + 实测值 + 建议线程数（见 4.1.2） | 用户主动查证时的落点 |
| **③ 设置 → 平台策略** | 四个平台横向对照表，每行一句说明 | 一次性建立正确预期 |
| **④ 完成后的总结行**（详情底部） | `耗时 5 小时 37 分 · 平均 78.4 KB/s · 百度账号级限速，理论下限 5 小时 7 分` | **装完第一个大文件后**，用户得到一个可验证的定性结论 |

> ④ 是设计上的一个小妙招：**用「已完成」任务做教育**。用户刚刚忍受了 5.4 小时，此刻他最想知道「是不是本该更快」。这一行给出「理论下限」，如果实际耗时接近下限，用户就彻底接受了这个产品——并且不会再怀疑。

## 4.3 是否需要「预期完成时间」的悲观提示

### 结论：**要，但不是全表的悲观提示，而是三个精确的阈值告警**

| 阈值 | 触发 | UI 表现 | 理由 |
|---|---|---|---|
| **ETA > 直链剩余有效期** | 单个任务/批次 | 「剩余」列橙色 + 末尾小 ⏰；详情里 `⚠ 按当前速度需 5 小时 12 分，直链仅剩 4 小时 30 分 → 将需要 1 次续链` | **这是本工具最独特、最有价值的预警**。它把「直链会过期」这个抽象约束变成了「你今晚会遇到 1 次中断」的具体预期 |
| **ETA > 12 小时** | 全表 | 顶部状态条右侧一行灰字：`预计全部完成：明天 08:40`；若超过明早 8 点，该行变橙 | 用户的真实决策是「今晚留不留机器开着」。给挂钟时间，不给「12.4 小时」 |
| **ETA 无法估算**（速度 0） | 单任务 | 剩余列 `—`，不显示任何时间 | 见 §1.1.5 防除零 |

### 4.3.1 为什么不做「悲观估计区间」（如「4 小时 – 9 小时」）

区间看起来严谨，实际是**把不确定性转嫁给用户去判断**。个人工具里，一句「4 小时 12 分」+ 一个「预计需要 1 次续链」的标注，比一个区间更有用。**这是明确的设计取舍：宁可给一个可能不准的单值 + 明确的例外告警，也不给一个诚实的区间。**

### 4.3.2 一个必须写进文档的矛盾点

ETA 与「续链」的关系是**非线性**的：续链期间（最长 60 秒 + 扩展响应时间）下载会停。所以 ETA 在有过续链历史的任务上会**系统性偏乐观**。处理：

- 任务发生过 N 次续链，每次按 **实测停顿长度** 累加进 ETA：`ETA = 纯下载 ETA + 已发生的续链停顿`。
- 更进一步（**v0.3 才做**）：按「已续链次数 × 平均续链耗时」外推未来的续链停顿。
- **v0.1 不做这层外推**，只在详情里显示 `已续链 2 次，累计停顿 1 分 47 秒`，让用户自己心里有数。

# 第六部分 · 发现的需求矛盾与待决问题

> 这一节是给实现者看的设计债。每一条都标明「影响哪个界面元素」。

## 矛盾 1 · `expires_at` 全部为 `None`，但界面需要「直链剩余」一列 ★最重要

**事实**：`platforms/baidu.py:508` 与 `platforms/quark.py:297` 都传 `expires_at=None`；`DirectLink.expires_at` 注释写「None 表示未知，按立刻下载处理」。
**冲突**：本文的 §1.1.10 与 §4.3 都依赖这个字段做「提前预警」。
**处置（三选一，建议 B）**：
- A. v0.1 就显示 `未知`（诚实但没价值）。
- B. **推送时由扩展侧补算**：百度知道 `expires=8h`（`models.py`/`ARCHITECTURE.md` 都写了），扩展可在取链时刻 + 8h 写入 `expires_at`。这是**改动最小、收益最大**的一条。
- C. 下载器侧收到任务时记录 `received_at`，按平台保守假设（百度 8h、夸克 6h、微云 2h）推算，并标注 `（估算）`。
**界面后果**：在 B 落地前，「直链」列所有行显示灰色 `未知`。**这一列仍然要保留**——它是 v0.2 提前续链的挂载点。

## 矛盾 2 · 「每平台并发数」在推送契约里叫 `options.workers`，但 `server.py` 读的是 `item.workers`

**事实**：`ARCHITECTURE.md` §3.1 的契约把 `workers` 放在 `options`；`server.py:71` 读 `item.get("workers", 4)`；`extension/background.js` 构造的 item 里**没有 `workers`**。
**后果**：所有任务实际都以默认 4 路开跑——**百度会以 4 路跑，实测会触发 403 降到 9 KB/s**。
**界面要求**：GUI **必须**对「平台上实际生效的线程数」有独立判断，不能相信推送来的值。方案：**GUI 侧按平台表兜底**（百度 1 / 微云 8 / 夸克 6 / UC 6），并在详情里显示 `线程数 1（平台默认；扩展未指定）`。这条也说明：**设置里的「每平台线程数」是权威来源，扩展的建议值只作参考**。

## 矛盾 3 · 取链失败的文件在下载器里不可见

**事实**：`injected.js` 为失败文件塞 `error/skipped`；`server.py._handle_task` 里 `if not item.get("url"): continue` 直接丢弃。
**后果**：100 个文件推送 82 个成功，GUI 认为「来了 82 个」，用户以为丢数据（§3.4 最后一段）。
**处置**：推送 payload 增加一个 `failed_items` 块（或 GUI 侧改为接收包含 `error` 的 item 并展示为「未取到直链」行）。**这是 GUI 侧必须提出来的接口变更，不是纯 UI 问题。**

## 矛盾 4 · 用户要「每平台并发数」，但百度线程数改了会掉速——设置项本身是陷阱

**冲突**：用户想「设 8 路会快」，实测 8 路降到 9 KB/s。**一个允许设置的参数，实际只应该有一个值。**
**处置**：设置项保留，但**百度那一行的数字框旁边必须常驻红字警告**，且改成 > 1 时**在下载中立即显示降速事件**（详情时间线：`已降到 9 KB/s，建议恢复 1 路 [恢复]`）。**不要**直接禁用输入框——自用工具的用户可能就是想做实验（`PLATFORMS.md` 里还挂着「待验证：限流期增加并发是否有效」），禁用掉反而挡住了实验。**给警告，不给禁令。**

## 矛盾 5 · 扩展每 30 秒轮询续链，而浏览器可能没开

**事实**：`ARCHITECTURE.md` §3.2 设计了扩展侧 30 秒轮询 `GET /api/pending-refresh`。若浏览器关闭/service worker 被回收，轮询停止，续链永远等不到。
**界面要求**：GUI **不能**把「等待续链」当成正常状态无限显示。必须有超时升级（本文定 60 秒）。并且需要在连接状态浮层里显示 **`扩展最后心跳：21:03（12 分钟前）`**——这是判断「为什么续链没人理」的唯一线索。**这意味着 `/api/health` 需要能被 GUI 用来推断扩展存活**（当前 `/api/health` 不记录来源，属接口缺口）。

## 矛盾 6 · 「同批任务直链有效期相同」是简化假设

**事实**：一次推送里每个 item 各自带 `refresh` 块，各自的 `expires_at` 理论上可能不同（例如 100 个文件是逐次调用 `/api/filemetas` 取的，前后可能跨几分钟）。
**影响**：§3.1 的「批次头统一显示有效期、行内留空」需要**先判断批次内 `expires_at` 是否全部相同（差值 < 1 分钟）**；不同则回退到逐行显示。**别把这个简化写死。**

## 矛盾 7 · `/api/task` 会为每个 item 起一个线程并**立即下载**，与「同时下载任务数」设置冲突

**事实**：`server.py.start_download()` 在收到请求时就 `threading.Thread(...).start()`，没有队列。
**后果**：推送 100 个文件 = 100 个并发下载，等于把「同时下载数」设置架空，且 100 × 8 连接会被平台立刻掐。
**界面要求**：GUI 想要「等待中」状态（§1.1.6 的 `queued`），**但这需要后端引入真正的队列**。在队列落地前，GUI 的「等待中」只能靠前端节流伪造（不推荐）或干脆全部显示为「下载中」。**建议：v0.1 就把「同时下载数」从设置里拿掉，等队列做好再加回来**——否则设置项是假的。

## 待决问题（需要用户/Lead 拍板）

1. **GUI 形态**：本机是「托盘常驻 + 窗口」，还是「浏览器标签页打开的本地页面」？后者与扩展同源更顺（`127.0.0.1` 可直接被扩展访问），但「关掉标签页就看不见」违背「过夜下载」场景。**我默认按「独立桌面窗口 + 托盘」设计**。
2. **直链有效期数据源**：走矛盾 1 的 A/B/C 哪条？影响「直链」列能不能立刻有值。
3. **「取链失败清单」的投递通道**：改 payload，还是让扩展 popup 自己承担、GUI 不感知？若 GUI 不感知，§3.4 的组头「82/100」就做不出来。
4. **是否需要「同时下载任务数」**：若后端不做真队列，这个设置项应当删掉（矛盾 7）。
