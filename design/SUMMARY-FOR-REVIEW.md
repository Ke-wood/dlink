## 二、开发过程中修掉的 3 个真实 Bug

这些都是实测发现的，不修会导致「工具看起来坏了」。

### Bug 1：百度任务实际跑 4 路，触发风控掉到 9 KB/s ★

`server.py` 读 `item.workers`，但扩展根本不发这个字段 → 所有任务按默认 4 路跑。
**后果**：百度实测 4 路会触发风控。用户会以为「这软件莫名其妙很慢」。

**修复**：`server.py` 改为按平台读 `profile`，百度强制 1 路。

### Bug 2：同名并发下载合并出多余字节 ★

`unique_dest()` 没有加锁。两个同名任务同时进来，都看到「文件不存在」→ 用同一个 `dest` → **共用同一个 `.parts` 目录** → 分段文件互相覆盖。

实测后果：29,701,389 字节的文件合并成 **29,832,461**，多出 131,072 字节，校验必然失败。

**修复**：加锁 + 预占路径。已写回归测试（8 线程并发取名，必须 8 个不同路径）。

### Bug 3：百度返回的 md5 是假的

百度 API 的 `md5` 字段是内部格式：`a1b2c3d4e5o6f7a8b9c0d1e2f3a4b5c6`（**含字母 o**，不是十六进制）。
真实文件 MD5 是 `e3b0c44298fc1c149afbf4c8996fb924`。

**如果直接拿来校验，必然 IntegrityError，白下一遍。**

**修复**：新增 `hashing.py`，非标准哈希直接丢弃，退回 size + 魔数校验。

## 四、GUI 两份文档的核心结论

### 信息架构（929 行）
- 主窗口唯一，详情用右侧抽屉
- 8 列任务表，进度条/百分比/状态在**一个单元格合成绘制**（省列宽）
- **速度必须 3 秒平滑**：百度恒 80KB/s，不平滑会显示成 `0/240/0/240` 锯齿，用户以为软件在骗他
- **「直链剩余」独立成一列常驻**——这是与普通下载器最大差别
- 状态必须拆：`校验中` 单独一个状态（1.5GB 算 SHA1 要几十秒，不拆会被当卡死）

### 开源参考（708 行，12 个仓库 star 数是 API 实值）
- **最该抄 Motrix**：每列定义 `{width,min,max,numeric}` + `clampColumnWidth()`，且「该列当前是否有意义」写成函数（无意义显示 `—` 而非 `0`）
- **最该避 JDownloader**：设置项淹没
- **技术栈建议 Web UI 而非 PySide6**：后端已是纯 HTTP/JSON，不引入第二运行时；反例 Persepolis（7,501★）13 个月没更新，Qt 打包耗死维护热情
- **新发现**：`hmjz100/LinkSwift`（**39,926★**）问题域重合 90%，其更新日志是现成坑表
- ⚠️ **别把并发数做成滑块**：滑块暗示「往右更好」，用户会拉到 8 路然后变慢到 3.07

## 五、需要你拍板的事项

### ① GUI 技术栈（最重要）

A. **Web UI**（本地 HTTP + 浏览器打开 / 可选套壳）
   - 优点：顺现有架构，零额外依赖，改样式快
   - 缺点：多一个标签页；需自己处理「关掉就看不见」

B. **PySide6 桌面原生**
   - 优点：真桌面窗口、托盘、系统集成好
   - 缺点：引入 Qt 依赖（约 100MB），打包麻烦

参考文档推荐 **A**。我的看法：**A 更符合你的现状**（后端已经全是 HTTP/JSON，扩展也在 127.0.0.1 上跑）。但如果你要「托盘常驻 + 过夜下载不让用户找不到窗口」，B 更稳。

### ② 并发数三层结构是否做

文档建议：平台默认 → **按 host 记忆** → 任务覆盖。
第 2 层我已经实现并测试了（`host_learn.py`）。要不要在 GUI 里暴露「该站点最佳 N 路 [重置]」？

### ③ 直链有效期数据源

百度/夸克/微云都不返回绝对过期时间。我已在扩展侧按 TTL 补算（百度 8h、夸克 6h、微云 2h）。
**这些是保守估计，可能不准。** 接受吗？

### ④ 夸克自动转存要不要保留

夸克分享文件不能直取，必须转存到你网盘根目录。当前是自动转存 + 不清理。
- 保留：方便，但会堆垃圾
- 改成「下载完成后自动删除转存的文件」：干净，但万一下载失败就没了
