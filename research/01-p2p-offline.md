# 01 · P2P / 离线下载 / 转存换通道 路线可行性评估

> 调研日期：2026-11-15
> 评估对象：能否让文件「不走」百度网盘那条被限速的下载通道。
> 前提事实（已实测，本文不再复核）：单连接 80.0 KB/s、聚合 ~100–130 KB/s 且与并发数无关、换直链不重置、换 CDN/UA/Range/PCS 接口全无效、xpan 官方 API 返回 `errno:9019 need verify`。
> **纪律说明**：本文严格区分「查到的说法」与「实测」。凡未在本机跑过的，一律标为「未验证」并给出验证方法。所有外部来源标注年份。

---

## 1. 一句话结论

**「有条件」——但条件不在 P2P / 离线下载 / 转存换通道这条线上。**

- **A（转存/换入口）、B（第三方云转云）、C（BT）、D（WebDAV/AList/客户端通道）这四条子路径，没有一条能绕开百度账号级的带宽封顶**；它们要么根本不产生新通道，要么在生产环境同样受 80 KB/s 限制。
- **真正存在的「其他路径」只有两条，且都是产品级而非协议级：**
  1. **百度网盘 PC 客户端的「优化速率：利用闲置带宽优化下载速率」开关**（官方内置的 P2P 加速，代价是分享闲置上行带宽）——这是唯一一个**合法、可得、可能把速度提到 MB/s 量级**的杠杆，**且尚未在本机实测**，是唯一值得立刻跑实验的点。
  2. **付费换取配额**（SVIP / 按天 VIP / 开发者付费能力）——本质是把限速变成商品价格，不是"绕过"。
- 一句话：**限速是账号级（服务端配额），不是通道级；凡是仍然用你这个 BDUSS 去取字节的路径，都逃不掉。要逃掉，必须让"字节不以你的账号身份从百度流出"，而这在合法前提下只有 P2P 加速和付费两条路。**

### A. 百度自带离线下载 / 分享转存是否产生新通道

#### A-1 转存后下载 → **不可行（已实测，无需重测）**

本机实测（`docs/BAIDU-SPEEDTEST.md` §2）：转存 → `/api/filemetas` 取直链 → 仍是 80 KB/s 量级。这是完全符合预期的：**转存改变的是文件的归属与目录，不改变"谁在下载"**，限速挂在账号维度，所以必然不变。此项**不需要再投入实验资源**。

#### A-2 分享给别人、让别人下载 → **不可行**

这条路的隐含假设是"别人的账号可能没被限速"。但它有两个致命问题：

1. **不解决你自己拿字节的问题**。除非你打算长期依赖别人的账号（你已明确否决多账号/账号共享）。
2. **对方也是普通账号**，按同样规则同样被限到 80 KB/s。

项目文档已实测：`/api/sharedownload`（分享直下）**即使登录也返回 `errno:118`**（BAIDU-SPEEDTEST.md §1.2）。即网页端"分享页直接下载"这条路本身就已经被封。

#### A-3 官方「获取分享下载地址」接口 → **不可行（本次调研的新发现，但结论仍是否）**

这是本次调研**唯一找到的、此前项目未记录的"新入口"**：百度开放平台有 `POST https://pan.baidu.com/apaas/1.0/share/download`，**可以直接从分享链接（short_url）取 dlink，不需要先转存到你的网盘**。

它看起来像是理想的绕行方案——直到看它的准入门槛：

| 门槛 | 内容 | 来源 |
| --- | --- | --- |
| **付费能力** | "文件分享服务为**付费开放能力**，购买服务后才可正式使用" | [接入指南](https://pan.baidu.com/union/doc/基础网盘服务/文件分享服务新/接入指南/)，更新 2026-09-10 |
| **企业主体** | "文件分享服务属于**企业开发者专属权益**，需要先完成**企业开发者认证**" | 同上 |
| **仅授权目录** | 第三方应用在网盘**只能拥有一个 `/apps/{appname}` 目录**，文件类接口须限定在权限内目录 | [权限与配额](https://pan.baidu.com/union/doc/使用入门/权限与配额/)，更新 2026-07-03 |
| **大文件禁止** | `13047 prohibit get large file link` —— **"无法下载大文件，请转存后下载"**；另有 `13046` 禁止下载目录 | [错误码说明](https://pan.baidu.com/union/doc/基础网盘服务/文件分享服务新/错误码/)，更新 2026-09-09 |
| **限流** | 未上线应用 **10 次/每小时**，最大授权用户 10 个 | 权限与配额，同上 |
| **`use_traffic` 参数** | 有 `use_traffic` 参数（"是否使用**极速下载流量**"），默认 0 | [获取分享下载地址](https://pan.baidu.com/union/doc/基础网盘服务/文件分享服务新/获取分享下载地址/)，更新 2026-09-09 |

**判定**：这条路要花钱、要企业资质、要过审、还不让下大文件。**对这个工具而言，投入产出比低于直接买 SVIP**。（`use_traffic=1` 的"极速下载流量"是唯一有趣的参数——它意味着"加速"在百度那里是一个明确的、可计费的开关，这也反向印证了 §1 的判断：**限速是商业策略，不是技术缺陷**。）

#### A-4 秒传 / 极速转存 → **不可行**

秒传（rapid upload）的本质是：**让服务端相信"这个文件的 md5 你已经有了"，从而跳过上传**。它优化的是**写入**方向，完全不产生读取方向的新通道。

源码佐证（本机已落盘 `research/src-openlist/seed_rapid.go`）：
```go
// RapidHashAlgos 返回百度网盘支持的秒传哈希算法（MD5）
func (d *BaiduNetdisk) RapidHashAlgos() []utils.HashType
```
以及 `util.go` 中的 `EncryptMd5`（md5 片段重排）。这是标准的秒传实现，与下载速度无关。

#### A-5 百度自带「离线下载」→ **不可行（方向错误）**

百度网盘的离线下载是「把公网链接的资源**拉进**你的网盘」。它的用途是**入**。你的问题在**出**。进去之后仍然要通过同一个账号级限速通道出来，净收益为零（甚至更差）。

### B. 第三方网盘「离线下载 / 云转云」

#### B-1 架构性结论：它们**没有**你的 BDUSS

先把关键事实钉住：**访问你百度网盘里的文件，必须有你的 `BDUSS` + `STOKEN`**（本机实测，BAIDU-SPEEDTEST.md §1.3；缺 `STOKEN` 一律 `errno:-6`）。

于是任何"服务端帮你下"的第三方，只有三种可能：

1. **不接入百度** → 根本无从下手；
2. **接入百度但用它们自己的账号** → 它们需要先把文件转存到自己账号，然后……**它们自己也是百度普通账号，同样被限到 80 KB/s**；
3. **要求你交出 BDUSS** → 这本身就是极高风险行为（等于交出账号）。

**MultCloud 的实际行为印证了第 1 种**：其[百度支持页](https://www.multcloud.com/cn/support-clouds/baidu.html)（访问 2026-11-15）在"新功能"部分反复描述的是**从 Google Drive / OneDrive / Yandex 等传到百度**的方向，标题即 "Transfer data on Baidu to Google Drive, OneDrive, Yandex..." 中的 "在 Baidu 上"更多指"把百度当目标盘"。它的产品形态是**云端调度器**——调度的是"谁向谁发请求"，**不是**"谁来付带宽"。

**同理评估其余候选**：

| 服务 | 是否支持"百度分享链接 → 服务端下载 → 你再下" | 判断依据 |
| --- | --- | --- |
| MultCloud | ❌（方向主要为"传入百度"） | 官方支持页，2026-11-15 访问 |
| AirExplorer | ❌ 同架构（云端调度），未找到百度"取出"证据 | 未找到明确来源 → **查不到** |
| 115 离线 | ❌ 只吃 magnet / BT / ed2k / http 直链 | 见 B-2 |
| 迅雷云盘 | ❌ 同 115，吃磁力/ed2k/http | 未找到百度分享支持 → **查不到** |
| 阿里云盘 | ❌ 不提供第三方离线抓取百度 | — |
| PikPak | ❌ 官方主打 **Torrent / Magnet / 社交站点视频链接** | [pikpak.me](https://pikpak.me/) "save links from Torrent / Magnet / Social Media" |
| Offcloud | ❌ 官方 FAQ 明说支持范围是 **HTTP / HTTPS / FTP / BitTorrent**，"任意**公开**站点" | [offcloud.com](https://offcloud.com/) FAQ，2026 |

#### B-2 为什么"百度分享链接"没法喂给离线下载（技术原因，重要）

百度分享页 `pan.baidu.com/s/xxx?pwd=yyy` **返回的是 HTML 页面**，不是文件本体。要拿到字节，中间必须串一串需要登录态的 API 调用：提取码校验 → `/share/list` → `/share/tplconfig` 取签名 → `/share/transfer` → `/api/filemetas` → 带 `BDUSS` cookie 请求 `d.pcs.baidu.com`（BAIDU-SPEEDTEST.md §1.1）。

一个"输入链接就下载"的通用离线服务**不可能**走完这条链——它没有你的 cookie，也没有你的提取码校验态。所以**能做这件事的服务，必然是专门逆向百度、并用自己的百度账号**的——回到 B-1 的第 2 种情况，速度一样是 80 KB/s。

> **这一条是 B 路径的充分反驳**：不是"暂时没有这样的服务"，而是**"这样的服务即使存在，也不会更快"**。

#### B-3 吞吐量级

对于"从百度取出"这一动作，无论哪家代劳，**理论天花板就是百度给该账号的配额**（本机实测 ~80 KB/s / 账号聚合 ~100–130 KB/s）。声称"极速"的第三方，要么不经过百度，要么虚假宣传。

### C. BT / P2P 路线

#### C-1 公网 BT 种子 → **不通用，但可作为「特定文件」的人工备选**

- **通用性：无。** 你的实际用例（网盘分享的 `VRQ1/PC.7z` 这类文件）通常**没有**公网种子。BT 依赖 swarm 中存在持种者；冷门/私有文件种子可用性接近 0。这不是"实现难度"问题，而是"物理上没有第二个持有者"的问题。
- **架构价值：有一个。** 如果文件**确实**在公网有活跃种子，则确实**完全绕开百度**，速度由 swarm 决定（可达 MB/s），且**零封号风险**。
- **是否值得纳入工具：** 值得作为一个**极低成本的提示性功能**（"检测到文件名可匹配公开种子索引"），但**不应作为主路径依赖**，也不应承诺命中率。
- **未验证：** 我没有做"A 文件是否有种子"的实测（需要真实样本 + 索引站访问，且索引站本身合法性存疑）。建议若要做，只做**用户手动提供种子文件**的入口，避免工具自动抓取种子索引带来的法律风险。

#### C-2 用百度自己的离线下载做中转 → **不可行**

见 A-5。

### D. 其他协议层思路

#### D-1 AList / OpenList（WebDAV、挂载） → **不可行（有官方原文，这是最强证据）**

AList 官方文档，**两个不同的页面各自独立地**给出了同样的结论：

1. [百度网盘驱动页](https://alistgo.com/zh/guide/drivers/baidu.html)（最后编辑 **2026/5/7**）：
   > **Official**: 官方接口，很稳定，但是文件比较大，需要修改 UA，**速度慢 (SVIP 速度快)**
   > **Crack**: 非官方接口，**似乎已经无法使用了**（原文带删除线）
   > 另注明：自定义破解 UA 一栏已标注 **"非官方接口已无法使用"**

2. [百度分享驱动页](https://alistgo.com/zh/guide/drivers/baidu_share.html)（最后编辑 **2025/4/23**）：
   > **"不能突破速度限制，请合理使用。"**
   > 且要求：`BDUSS` 参数的账号 **必须使用百度超级 SVIP 会员**

3. 中文检索中亦有同向说法（2022-12，公众号转载）："Alist 也并不能解除网盘限速，百度云这种网盘没有会员则依然速度感人"。

**结论**：AList 是"另一种**访问方式**"，不是"另一种**带宽**"。它解决的是"用 WebDAV 在播放器里看片"，不解决"更快地把字节搬回来"。**本项目不应在 AList 上再投入时间。**

#### D-2 AList 的 `crack` 接口 —— **未验证，唯一值得盲测的协议层假设**

**源码事实**（本机已落盘，`research/src-alist/util.go:182-203`，`research/src-openlist/util.go:228-248` 两份实现一致）：

```go
func (d *BaiduNetdisk) linkCrack(file model.Obj, _ model.LinkArgs) (*model.Link, error) {
	param := map[string]string{
		"target": fmt.Sprintf("[\"%s\"]", file.GetPath()),
		"dlink":  "1",
		"web":    "5",          // ← 关键
		"origin": "dlna",       // ← 关键
	}
	_, err := d.request("https://pan.baidu.com/api/filemetas", http.MethodGet, ...)
	return &model.Link{
		URL:    resp.Info[0].Dlink,
		Header: http.Header{"User-Agent": []string{d.CustomCrackUA}}, // 默认 "netdisk"
	}, nil
}
```

**为什么它值得测**：项目文档已排除的是"换 UA""换 clienttype""换 CDN 主机"，但**没有排除**「**用 `web=5&origin=dlna` 这个特定 origin 取到的 dlink** + 配套 `UA: netdisk`」这一**组合**。百度对不同 `origin` 可能走不同的限速策略（dlna 是"投屏/媒体"语义，历史上被当作特殊通道）。

**为什么它大概率不行**：AList 官方已在文档里把它标为"似乎已经无法使用"（2026-05）；且就算能取到链接，**限速若在账号维度**，换 origin 也没用。OpenList 仍保留该分支（默认仍是 `official`），说明它"能取到链接"，但不代表"不受限"。**"能下载" ≠ "不受限"**，这正是必须实测的理由。

**→ 具体实验方案见 §3 实验 2。**

#### D-3 BaiduPCS-Go 等第三方客户端 → **不可行（有原作者原文）**

`research/src-pcsgo/README.md:952`（已落盘源码 README）：

> 普通用户请将 `max_parallel` 和 `max_download_load` 都设置为 1，**调大线程数只会在短时间内提升下载速度，且极易很快触发限速，导致几小时至几天内账号在各客户端都接近 0 速。本软件不支持普通用户提速。**
> SVIP 用户建议 `max_parallel` 设置为 10 以上……实验表明可以稳定满速下载。

这段话**同时**印证了本项目两条实测结论：①并发无效且加剧风控；②SVIP 才是分水岭。**建议把这条引用进项目主文档，它是"别在协议层继续挖"的最权威背书。**

#### D-4 百度网盘 PC 客户端「优化速率 / 利用闲置带宽」 → **未验证，但这是首选实验**

**这是本次调研发现的、最可能真正有效的合法杠杆。**

- **功能形态**：百度网盘 PC 客户端 → 设置 → 传输 → 「**优化速率：利用闲置带宽优化下载速率或换取积分**」→ 勾选「优化速率模式」。默认**不开启**。
- **来源与年份**（均为"查到说法"，非实测）：
  - CSDN《提升百度网盘下载速度:启用闲置带宽优化》，2023-10-20：开启后"会比平常下载的几百 kb 速度提升很多"。
  - CSDN《百度网盘不限速_利用闲置宽带优化速率》，2022-09-23："从几 KB/S 提升到 MB/S"。
  - 今日头条，2023-03-09 / 2023-03-25：同一功能。
  - 公众号，2023-11-05：实测"几十或者上百 KB …开启后上升到 **1.2 MB/s**"，并提示"下载完之后要关掉，避免影响上网速度"。
  - 3DMGAME《百度网盘下载速度慢解决办法一览 2025》，2025-01-07：仍列为解法之一。
  - B 站视频标题《特大喜讯!!百度云盘不限速啦!!打开优化速率就可以!!》，2025-04-27。
- **反向证据（必须一并说明）**：
  - 系统评测《3个方法解决百度网盘限速（2026-03-25）》([runningcheese.com](https://www.runningcheese.com/baidu-netdisk-speed)，页面更新 2026-04-19) 的核心判断是：**"最近，百度网盘加速方法悉数失效。"** 其列出的三条现行方法分别是「公益解析」「LinkSwift（无加速）」「1 元 VIP（买一天 SVIP）」。其中「公益解析」在该页评论区 **2026-04-19 已被反馈"失效了"**。
  - 同一页评论 2025-06-06："HD2A 已经把毒盘排除在外了"。
- **技术解释（为什么它可能有效）**：这不是绕过服务端限速，而是**百度官方把"用你的上行带宽换下载加速"做成了一个交易**。你的字节里有一部分来自其他用户的 P2P 做种，不经过计费通道，所以能突破 80 KB/s。**这恰好是题目所问"让字节不走百度那个被限速的通道"——而且它是唯一一个百度自己承认的合法实现。**

**风险**：这是"用你的上行带宽/隐私换速度"的合约（相当于当 CDN 节点），长期挂机会持续占用上行；且百度可随时调整/下线该策略（这可能就是"2025 年后悉数失效"说法的一种解释）。必须实测确认**当前版本是否还有此开关**。

**→ 具体实验方案见 §3 实验 1（最高优先级）。**

#### D-5 "模拟 PC 客户端协议" → **不可行（大概率）**

判断依据：客户端的下载**同样是走 `d.pcs.baidu.com` 拿 dlink**（`research/src-pcsgo/baidupcs_download.go` 中 `LocateDownload` / `LocatePanAPIDownload`，以及 AList 的 `linkOfficial` 都指向同一条链路）。既然服务端按账号下发配额，那么"用客户端相同的请求头"并不改变配额。项目文档已实测"换 clienttype / 换 UA 无效"，与此判断一致。

**唯一例外**仍是 D-4——但那不是"模拟协议"，而是**客户端里那个独立的 P2P 加速功能**，属于产品能力，不可由协议复现。

## 3. 「有条件」的实验方案（可证伪、可立即执行）

> 设计原则：每条假设都给出**明确的成功判据**与**明确的失败判据**，以及"失败后应当得出什么结论"。**禁止**用"再试几次也许就快了"作为判据。
> 通用要求：每次实验前**重置对照**（重新取链 + 静置 5 分钟），并把结果记录到 `docs/BAIDU-SPEEDTEST.md` 末尾。

### 实验 1（最高优先级）：「优化速率 / 闲置带宽」是否仍存在且有效

**假设 H1**：开启「优化速率」后，同一文件的下载速度显著高于 80 KB/s，且不随并发增加而劣化。

**步骤**：
1. 确认客户端版本：打开百度网盘 PC 客户端 → 设置 → 关于。记录版本号。
2. 进入 设置 → **传输**，查找「优化速率 / 利用闲置带宽优化下载速率或换取积分」开关。
   - **若开关不存在** → H1 **立即判负**，Q1（开关是否仍存在）回答"否"，本条路线作废，跳过后续步骤。
3. 若存在：勾选「优化速率模式」，确认协议同意，保存。
4. 用**同一个文件**（`VRQ1/PC.7z`，29,620,737 字节）测速，**同时**用浏览器/客户端各测一次，记录 30 秒平均速度。
5. 对照组：在**关闭**该开关后重复步骤 4（或对比历史实测 80 KB/s）。

**成功判据（必须同时满足）**：
- 平均速度 **> 500 KB/s**（即 6 倍以上基线，排除噪声），且
- **稳定持续 ≥ 30 秒**（排除突发/缓存），且
- 关闭开关后**回落到 ~100 KB/s 以内**（证明因果，而非网络环境变化）。

**失败判据（任一成立即判负）**：
- 速度仍在 80–150 KB/s 区间；
- 速度短暂冲高后回落到基线（说明只是 TCP 慢启动/本地缓存）；
- 开关存在但点击后提示"功能已下线/仅限会员"。

**若成功** → 写入主文档：**这是唯一可用的合法提速路径**，工具应把"检测客户端优化速率开关状态"作为提示项（注意：**这只是提示，工具自身无法从 API 侧获得该加速**）。
**若失败** → 得出强结论：**百度已封堵 P2P 加速**，"P2P/离线下载/换通道"整条路线在合法前提下**全线不可行**，工具应停止在该方向投入，转而做"限速告知 + 断点续传 + 排队后台慢速拉取"的工程优化。

---

### 实验 2（次优先级，成本 < 30 分钟）：`crack` 链路（`web=5&origin=dlna`）是否不受限

**假设 H2**：通过 `origin=dlna` 取到的 dlink，配合 `UA: netdisk`，速度显著高于官方 `filemetas` 链路。

**前置**：已有可用 `BDUSS` + `STOKEN`（BAIDU-SPEEDTEST §1.3），且文件已在自己网盘（转存过）。

**步骤**（在现有 `probe/` 下新增脚本，**不改 `src/`**）：

```python
# probe/probe_dlna_origin.py  —— 只读探测，不改项目代码
# 目的：对比 3 条取链路径的实测速率
#   A) 官方: /api/filemetas?dlink=1&fsids=[fsid]
#   B) crack(web=5,origin=dlna): /api/filemetas?target=["/path"]&dlink=1&web=5&origin=dlna
#   C) media: /api/mediainfo?type=VideoURL&...&origin=dlna   (仅视频)
# 对每条拿到的 dlink，用 Range: bytes=0-8388608 拉 8 MB，计时算 KB/s，
# UA 分别试: "netdisk" / "pan.baidu.com" / 默认浏览器
```

**执行要求**：
- 每条路径**间隔 5 分钟**，避免账号级风控串扰（这是本项目已实测的坑：换链会越测越慢，74→43）。
- 每条路径至少跑 **3 次**，取中位数。
- 记录 `HTTP 状态码`（尤其留意 `31119 / 31329 hit black userlist`，见 AList 文档所列错误）。

**成功判据**：
- 某条路径中位数 **> 300 KB/s**，且 3 次中有 2 次稳定，且**不与并发正相关**（排除错觉）。

**失败判据**：
- 三条路径速度都在 **60–150 KB/s** 区间（差异 < 2 倍）→ 判定"限速在账号维度，与取链 origin 无关"，H2 判负。
- 出现 `31119/31329` 或 403 → 判定"该 origin 已被风控标记"，H2 判负**且加重账号风险**，应立即停止。

**若失败**（我预判的概率高）→ **这是本报告最有价值的"证伪"**：可以**永久关闭**"协议层绕行"这个方向，避免团队继续消耗。建议把这个实验作为**结案实验**，跑完就写进主文档。

---

### 实验 3（廉价，30 分钟，用于量化"付费是否真解限"）

**假设 H3**：SVIP（或按天 VIP）会解除账号级限速。

**步骤**：购买最短周期（按天，市价 0.3–1 元，来源：runningcheese 2026-04 评测提到的"1 元 VIP"做法）；用同一文件、同一脚本重跑 BAIDU-SPEEDTEST §2 的并发对照（1/2/3/5 路）。

**成功判据**：单连接 **> 5 MB/s**，且 3 路以上并发的聚合速度**随路数上升**（说明是连接级而非账号级限制）。

**价值**：这一条即使"成功"也不算技术突破，但它能给出**"花钱能买到多少"的定量结论**，从而让"值不值得做工具"这个决策变成一个明确的算术题（当前 29.6 MB 文件在 80 KB/s 下需 **6.2 分钟**；若 SVIP 达 5 MB/s 则需 **6 秒**）。

> ⚠️ 提醒：从第三方渠道买"共用账号"违反百度用户协议（[开放平台使用规范](https://pan.baidu.com/union/doc/)明列"多人共享个人网盘账号及会员权益"为禁止行为）。**本项目工具不应内置或引导此类做法**，此实验仅用于摸清价格-性能曲线，结论写入报告即可。

### 实验 4（可选，仅当用户有真实"特定文件"需求时）：BT 命中率抽样

**做法**：取 20 个你**真实需要**的百度分享文件名，人工在 1–2 个公开索引站检索，统计命中且**有活跃 seed** 的比例。

**成功判据**：命中率 > 20%（值得做入口）。
**失败判据**：命中率 < 5% 或命中的种子均无 seed → C 路径不纳入工具。

> **未做**：本报告没有执行该抽样（缺少你的真实文件清单，且自动抓取种子索引有法律风险）。

## 4. 风险

### 4.1 账号封禁风险（**这是最高风险，且已被实测触发过**）

| 行为 | 风险等级 | 依据 |
| --- | --- | --- |
| 高并发分段（8/16 路） | **高** | 本机实测：16 路时 **6/16 直接 403**，8 路时 6 路返回 403（BAIDU-SPEEDTEST §2.1） |
| 反复刷新直链试探限速 | **中高** | 本机实测：连续换链后 74→43 KB/s，**账号级累积风控**（§2.2） |
| 使用 `origin=dlna` / 非浏览器 UA 等非官方链路 | **高** | AList 文档列出 `31119 / 31329 hit black userlist`；`31326 user is not authorized, hitcode:119` |
| BaiduPCS-Go 大线程 | **高（作者明确警告）** | README：调大线程"极易很快触发限速，导致几小时至几天内账号在各客户端都接近 0 速" |
| 把 BDUSS 交给第三方服务 | **极高** | 等同于交出账号；且本项目已实测 Edge cookie v20 加密不可外部读取（说明百度/浏览器本身也在防这个） |

**结论**：**任何"更快"的尝试，本质上都在和提高风控强度对赌，而风控的惩罚是"账号接近 0 速数天"**。对一个"下载工具"而言，这是把可用性换成速度，不划算。

### 4.2 法律与合规风险

- [百度网盘开放平台使用规范](https://pan.baidu.com/union/doc/)明确禁止："违规作弊、侵犯百度网盘的商业利益，比如**多人共享开发者账号、多人共享个人网盘账号及会员权益**"、"利用个人网盘账号进行企业建站、图床、搭建网盘迁移工具等产品行为"，并声明"会采取多种**封禁措施**，并保留追究法律责任的权利"。
- **"搭建网盘迁移工具"**这一条与 B 路径（云转云）直接相关：**即便技术上可行，做成产品也是有明确协议风险的。**
- 以"公益解析"为代表的第三方解析站（本次检索中出现且已被反馈失效）游走在灰色地带，**不应作为工具的后端依赖**。

### 4.3 稳定性风险

- 所有非官方接口（`crack` / `dlna` / 第三方解析）**随时失效**——AList 文档已亲自演示了这个过程（"似乎已经无法使用了"，2026-05）；runningcheese 评测 2026-04 的说法是"加速方法**悉数**失效"。
- 依赖第三方服务 = 依赖一个**你无法观测可用性**的黑盒。
- 相比之下，**官方 `filemetas` 链路稳定但不快**。

### 4.4 隐私风险

- 第三方离线/云转云服务需要文件内容经其服务器中转，等于把文件交给第三方。
- 「优化速率」功能要求分享闲置上行带宽，等于让你的机器参与 P2P 网络。

## 6. 对工具设计的直接建议（基于以上结论，不动代码）

1. **不要**把 A/B/C 任何一条作为功能路径实现——没有一条能提升速度，但每一条都会让工具从"下载器"变成"违规工具"。
2. **可以**在工具里做**一次性提示**："若需 > 100 KB/s，请检查百度网盘客户端『设置 → 传输 → 优化速率』开关"（前提：实验 1 证实该开关仍存在）。这是**零风险、可能高收益**的一个 UI 文案。
